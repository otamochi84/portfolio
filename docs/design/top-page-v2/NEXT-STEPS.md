### Worksカードの表現

「額縁の中で絵が揺れている」形。**枠は静止し、中の画像だけがそよぎ続ける。**

- 枠: `1px solid #e5e7eb` ＋ 全周12pxの余白、`overflow: hidden`
- 揺れ: `@keyframes wcardImageSway`。最大1.3°／2.8s／無限ループ、支点は画像の上端中央
- **サインカーブを21点（5%刻み）で刻み `linear` で繋いでいる。** 粗いキーフレーム＋`ease-in-out` だと、タイミング関数が各区間に個別に適用されて境目ごとに減速→停止→加速が起き、カクついて見えるため
- `will-change: transform` はホバー中だけ（常時だとカード数ぶんの合成レイヤーを確保してメモリを食う）
- `@media (hover: hover)` 内。`prefers-reduced-motion: reduce` で無効化

キービジュアルの風鈴からインスピレーションを得たが、**KVは今後差し替える前提なので風鈴そのものに依存する見た目にはしていない**（吊り下げ線などは描かない）。借りたのは「揺れる」動きだけ。

## Worksカードの見た目の決定事項（2026-08-11／蒸し返さないこと）

**枠線を廃止し、生成りの背景色＋にじむ影で輪郭を出す形に決めた。**

一時トグル（`tmpcanvas` 接頭辞）で4案を実機比較して決定。採用したのは「生成り `#faf8f4` ＋ 影2枚重ね、枠線なし」。一時コードは削除済み。

### 影を2枚重ねる理由

1枚目（ambient・オフセット0）が**横**の境界を作り、2枚目（key・下方向オフセット＋負スプレッド）が接地感を作る。**2枚目だけだと構造上どうしても影が真下に寄り、横の境界がほぼ消える**（これが比較中に出た「横の境界がわかりにくい」という指摘の正体）。

### 検討して却下した案

| 案 | 却下理由 |
|---|---|
| **織り目テクスチャ**（`repeating-linear-gradient` で画布の目を描く） | 等間隔の格子は織り目ではなく**方眼紙**に見える。「方眼紙に絵は描かない」。本物の織り目は不規則で、CSSの規則的な格子では原理的に再現できない |
| **イーゼルの線**（受け木＋脚） | イーゼルに見えなかった |
| **四隅のコーナーマーク**（トンボ風） | 好みに合わなかった |
| **罫線グリッド**（カードを囲まず全体を表に見せる） | 実装前に却下。余白たっぷりの基調と喧嘩する／「額装された作品」の見立てが消える／カードが2〜3枚では表に見えない |
| **ずらし影 8px**（ぼかしゼロ・ネオブルータリズム風） | 装飾が渋滞して見える。3px・5pxまで落とした版も比較したが、最終的に無しを採用 |

### 写真を「手書き風」にする件

CSSフィルタやSVGフィルタで写真を手書き風にするのは**品質が出ないので採らない**。安っぽい加工に見える。

なお、Notionカテゴリの画像に手描きイラストを使えば、CSSの小細工なしで「絵」に見える（Notion Consultingのカードが実例）。この方向で画像を揃えるほうが確実。

### 実装上の発見（再利用できる知識）

`box-shadow` は**先に書いたものが手前に来る**。不透明なずらし影とにじむ影を併用すると下辺が濁る問題は、**不透明な影を先頭に置けば解決する**（後ろに置くと二重に暗くなる）。今回は最終的にずらし影を採用しなかったが、同種の実装をするときに効く。

## 画像の扱いの決定事項（2026-08-10／蒸し返さないこと）

この件は**過去に2回、同じ議論を繰り返している**。結論を残す。

### 原寸は縮小しない。軽量化はsrcsetでやる

**アップされた画像の寸法は縮小しない。** 大橋さんが「アップ前にサイズ調整するのは手間」「画質は落としたくない」という前提のため。`webpQuality` を下げるのも画質低下なので不可。

そのうえで軽くするため、**Worksカードにだけ srcset を入れた**（`downloadCardImage()`）。フルサイズ版はそのまま残し、800px版・1200px版を追加生成してブラウザに選ばせる。

| | 対応 |
|---|---|
| Worksカード | srcset対応（800 / 1200 / 原寸） |
| KV・About写真・本文画像 | **対応しない。** 全幅〜記事幅で表示するので原寸が適正 |

実測（Local Work in Nara、原寸1920×1280 / 952KB）: モバイルで **952KB → 187KB（80%減）**。画質の劣化はない（表示サイズに合う解像度を渡しているだけ）。

### srcsetのw値には「実際に出力された幅」を書く（重要）

sharpの `withoutEnlargement: true` により、**要求幅より元画像が小さいと縮小されず元の幅で返る**。ここで要求値をsrcsetに書くと、ブラウザが解像度を誤認して拡大表示し**かえって粗くなる**。

実際に 1222px の画像で発生しうるケースだった。必ず sharp の metadata から実出力幅を読んで書くこと。

同幅の候補が並ぶ無駄を避けるため、`cardImageShrinkRatio = 0.9`（縮小後が原寸の90%以上なら作らない）で弾いている。

### 小さい画像がアップされたときの周知方法

長辺1200px未満だと `.wcard-image` の `aspect-ratio: 3/2` ＋ `object-fit: cover` で引き伸ばされ粗くなる。**ファイル側は拡大しない（`withoutEnlargement`）ので、これはCSS表示上の話。**

周知は**Notion親ページ「HP」→ `HP_Works` →「📝 プロパティ構成」表の「画像」行に注意書きを書く方式**に決めた。検討して却下した案:

- **プロパティの説明欄** → NOTION.mdの規則「データベースのプロパティに説明を付けない」に反する
- **ビルドログに警告** → 大橋さんがビルドログを読む運用ではない
- **ビルド時にNotionへコメント投稿** → ビルドごとにコメントが溜まる（重複排除の実装が必要）／ビルドが書き込み処理を持つ設計になる／気づくのがアップ後になる。**そもそも起こりにくい事象なので手間に見合わない**

### 既知の小さな問題（本番影響なし）

`public/notion-images/` は毎ビルド再ダウンロードするが**古いファイルを消さない**ため、バリアントの幅を変えると孤児ファイルが残り、Astroのpublicコピーで未参照のまま `dist` に入る。

**本番（Cloudflare Pages）はクリーンな状態からビルドするので影響しない。ローカルのみの話。** 気になるならビルド前に `public/notion-images/` を空にする npm script を足せば解決する（毎回再ダウンロードしているので削除してもコストは増えない）。
- `projects/[slug].astro` の `interface Props` が `any` のまま。`notion.ts` の `ProjectItem` 型を使えば型安全になる
- `getPageBlocks()` が本文画像を1枚ずつ直列にダウンロードしている。枚数が増えるとビルド時間に効く（`/works/notion/` で約2.9秒）
- 画像のローカル化に失敗した場合、画像は静かに消える。ビルドログに `画像のローカル化に失敗したので表示しません` が出るので、デプロイ時はログを確認すること

## 作業の進め方

コード実装は `implementer` サブエージェント（Opus 5・effort high）に委任し、メインスレッドがレビューして修正指示を返すサイクルで回す。
**呼び出し時に `model` パラメータを渡さないこと**（フロントマターの指定を上書きしてしまうため）。

比較して決めたいものは、**一時トグルを仕込んで実機で見比べてもらう**手法が有効だった（採用後に一時コードを全削除する前提で作る。`grep` で拾える接頭辞を付けておくと撤去が楽）。
